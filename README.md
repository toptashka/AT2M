# CRM «ИТ Школа Ростелекома» (RTK CRM)

Веб-приложение для управления партнёрствами с учебными заведениями: заявки на одобрение, взаимодействия по этапам Workflow, справочники, документы и отчёты.

## 2. Технологии и архитектура

| Компонент | Реализация |
| --- | --- |
| Frontend | React 19.2, Vite 8.3, JavaScript/JSX, CSS, Fetch API |
| Backend | Python 3.11 в Docker, FastAPI 0.103.1, SQLAlchemy 2.0 |
| База данных | PostgreSQL 15 |
| Аутентификация | Keycloak 22.0.4, JWT RS256 |
| Файлы | MinIO, S3-совместимый API через boto3 |
| Excel | OpenPyXL: импорт `.xlsx`, экспорт `.xlsx` |
| PDF | ReportLab со встроенным шрифтом, поддерживающим кириллицу |

Браузер обращается к Keycloak для входа и к FastAPI для работы с данными. Backend проверяет токен и права, хранит записи в PostgreSQL, а содержимое вложений — в MinIO. Для имён и списка КАМов backend обращается к Keycloak Admin API.

В режиме разработки Vite проксирует `/api` на `localhost:8000`, а `/auth` на `localhost:8080`, убирая префикс `/auth`. В рабочем размещении соответствующие маршруты нужно настроить в reverse proxy.

Docker Compose запускает **PostgreSQL, Keycloak, MinIO и backend**. Frontend в текущем Compose отсутствует и запускается отдельно. Keycloak использует режим `start-dev`; эта конфигурация предназначена для локального стенда.

## 3. Локальный запуск

### 3.1. Требования

- Docker и Docker Compose v2.
- Node.js 20.19+ в ветке 20 либо 22.12+ и npm — согласно требованиям установленного Vite.
- Свободные порты `5173`, `8000`, `5432`, `8080`, `9000`, `9001`.

### 3.2. Переменные окружения

Пример `.env` в корне проекта. Пример структуры, значения необходимо заменить:

```dotenv
POSTGRES_USER=admin
POSTGRES_PASSWORD=replace_with_database_password
POSTGRES_DB=rtk_crm
KC_ADMIN=admin
KC_ADMIN_PASSWORD=replace_with_keycloak_admin_password
KEYCLOAK_URL=http://keycloak:8080
KEYCLOAK_REALM=rtk_crm
KC_CLIENT_ID=frontend-app
KC_PUBLIC_KEY=replace_with_realm_public_rs256_key
ENCRYPTION_KEY=replace_with_fernet_key
MINIO_ENDPOINT=http://minio:9000
MINIO_ROOT_USER=admin
MINIO_ROOT_PASSWORD=replace_with_minio_password
```

`DATABASE_URL` передаётся backend существующим `docker-compose.yml` на основе параметров PostgreSQL. При запуске вне Compose его нужно задать отдельно.

`ENCRYPTION_KEY` должен быть постоянным Fernet-ключом. Для новой установки его можно получить после сборки образа:

```sh
docker compose build backend
docker compose run --rm --no-deps backend python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Запишите полученное значение в `.env`. **Для существующей БД используйте прежний ключ:** замена ключа не расшифрует ранее сохранённые данные. Не публикуйте `.env` в репозитории.

### 3.3. PostgreSQL, Keycloak и MinIO

```sh
docker compose up -d db keycloak minio
docker compose logs --tail=100 db keycloak minio
```

Дождитесь готовности сервисов. В Keycloak настройте:

1. Realm `rtk_crm`.
2. Клиент `frontend-app`. Текущий frontend использует вход по логину/паролю с `grant_type=password`, поэтому клиент должен разрешать Direct Access Grants и работать без секрета в браузере.
3. Роли `Пользователь`, `Руководитель`, `Администратор` в realm либо в клиенте `frontend-app`.
4. Учётные записи с нужными ролями. Для отображения ФИО заполните `firstName` и `lastName`.
5. Публичный RS256-ключ realm в `KC_PUBLIC_KEY`: тело ключа либо корректно оформленный PEM. Приватный ключ приложению не передаётся.

Backend использует `KC_ADMIN`/`KC_ADMIN_PASSWORD` либо `KEYCLOAK_ADMIN`/`KEYCLOAK_ADMIN_PASSWORD` для чтения списка сотрудников через Admin API. Эти учётные данные должны иметь соответствующие права. Автоматического создания realm, клиента и демонстрационных пользователей текущий Compose не выполняет.

Дополнительно поддерживаются `KC_ISSUER` и `KC_AUDIENCE`. Указывайте их только в соответствии с фактическими `iss` и `aud` токена. Backend проверяет `azp` на совпадение с `KC_CLIENT_ID`.

Тестовые логины и пароли создаются администратором стенда и передаются участникам демонстрации отдельно. Наличие конкретных учётных записей и паролей из прежнего README не гарантируется.

### 3.4. Backend и инициализация

```sh
docker compose up --build -d backend
docker compose logs --tail=100 backend
```

При старте backend создаёт отсутствующие таблицы и добавляет недостающие колонки через `schema_upgrade.py`. Если таблица этапов пуста, автоматически создаются 14 начальных этапов. После настройки Workflow количество этапов может отличаться от 14.

**Для обычного запуска `seed.py` не нужен.** Он добавляет демонстрационные учреждения, программы и партнёрства, а не только этапы. Не запускайте его или `create_demo_data.py` поверх рабочей БД для устранения ошибок.

### 3.5. Frontend

В отдельном терминале:

```sh
cd web

```

Для сборки:


Результат находится в `web/dist`. Его публикация и настройка reverse proxy выполняются отдельно.

## 5. Основные сценарии

### 5.1. Заявка и одобрение

КАМ выбирает учреждение и направление из справочников и отправляет заявку. Она сохраняется в `partnership_requests` со статусом `pending` и отображается в «Мои заявки». **Взаимодействие в этот момент не создаётся.**

Руководитель видит заявку во «Входящих запросах». При одобрении выбирается ответственный КАМ и создаётся одно взаимодействие на первом этапе Workflow. Повторное решение по рассмотренной заявке возвращает `409`. Отклонение не создаёт взаимодействие; статус остаётся доступен заявителю.

### 5.2. Workflow

Администратор добавляет, переименовывает, перемещает и удаляет этапы, задаёт обязательные условия завершения. ID этапа не зависит от его позиции в списке.

Удаление используемого этапа требует соседнего этапа для переноса взаимодействий. Единственный оставшийся этап удалить нельзя. Файлы и комментарии удалённого этапа переносятся в соседний; исторические снимки сохраняются в БД, но история удалённого этапа не выводится в текущем интерфейсе.

Переход вперёд проверяет обязательные условия. Наличие документа определяется сервером. Переход и возврат требуют комментарий. Последний этап завершается отдельным действием: само попадание на него не завершает взаимодействие.

Изменения защищены версией Workflow. При `409` нужно обновить данные и повторить действие.

### 5.3. Дедлайны

На Главной у руководителя и администратора есть кнопка **«Сроки этапов Workflow»**. Для каждого этапа задаётся от 1 до 3650 календарных дней; пустое поле отключает дедлайн.

Дата рассчитывается при фактическом входе на этап по московскому времени. При возврате отсчёт начинается заново. Будущие этапы получают дату при входе на них. Сроки отображаются в карточке и блоке «Ближайшие сроки».

Изменение длительности пересчитывает активный этап от сохранённой даты входа. Если у старой карточки она отсутствует, отсчёт начинается в момент настройки. Завершённые взаимодействия не пересчитываются. Значений по умолчанию нет — сроки нужно заполнить.

### 5.4. Карточки и документы

Карточка загружает контакты учреждения, ПО, вендора, реквизиты договора, статусы лицензии и передачи, комментарии и файлы по этапам. Изменения сохраняются на сервере. Пустая должность не выводится. Точная дата окончания лицензии хранится отдельно от длительности в годах.

Поддерживаются вложения `.png`, `.jpg`, `.jpeg`, `.pdf`, `.zip`, `.gzip`, `.gz`, `.rar`, `.doc`, `.docx`, `.xls`, `.xlsx`. Размер файла — от 1 байта до 50 МБ.

Содержимое хранится в bucket `rtk-crm-documents`, метаданные и ключ объекта — в PostgreSQL. Загрузка, скачивание и удаление проверяют доступ к взаимодействию. Файлы завершённых этапов доступны только для чтения. Ошибка MinIO не выдаётся за успешное сохранение или удаление.

### 5.5. Импорт справочников

Модуль поддерживает `.xlsx`, предварительную проверку, сопоставление столбцов и исключение строк. Старый формат `.xls` для импорта каталогов не поддерживается, хотя может храниться как вложение.

Типы загрузки: учреждения, ИТ-направления и программы, продукты и вендоры, контакты, сквозной реестр, списки студентов для выбранного взаимодействия.

**Сквозной импорт наполняет справочники и не создаёт партнёрства или заявки на одобрение.** Импортированные справочные значения доступны для фильтров и последующего создания заявки. Создание взаимодействия выполняется отдельно после одобрения либо руководителем напрямую.

### 5.6. Аналитика и отчёты

У КАМа нет блоков «Моя эффективность» и «Эффективность и нагрузка КАМов». Руководитель видит нагрузку именно КАМов. Дублирующие фильтры «Все продукты» под графиками удалены; верхний фильтр ПО сохранён.

Поддерживается экспорт взаимодействий в PDF и XLSX с серверной проверкой области доступа. PDF встраивает `web/src/assets/fonts/RostelecomBasis-Regular.ttf`, поддерживает кириллицу и переносы текста. Файл шрифта должен быть доступен backend.

**Ограничение экспорта:** текущий frontend передаёт в API только период (`start_date`, `end_date`). Остальные фильтры таблицы и выбранные колонки автоматически не переносятся в серверный экспорт. Нельзя считать выгрузку точной копией отфильтрованного представления по КАМам, учреждениям или продуктам. Конечная дата в текущем запросе сравнивается с timestamp без расширения до конца суток.

## 6. Хранение данных и безопасность

Основные сущности: `universities`, `programs`, `workflow_stages`, `partnerships`, `partnership_requests`, `partnership_comments`, `attachments`, `students`, `audit_logs`, `workflow_state`, `partnership_state`, `catalog_import_jobs`, `catalog_managers`.

Backend проверяет подпись JWT RS256, срок действия, `sub`, `azp` и роль. При отсутствии `KC_PUBLIC_KEY` доступ запрещён; при отсутствии `ENCRYPTION_KEY` запуск прекращается. Чужие карточки для КАМа закрыты целиком, а не выдаются с маскированными контактами.

Часть данных защищена на уровне полей с помощью Fernet. Это не означает шифрование всех таблиц и объектов MinIO. Реализована запись ряда действий в `audit_logs`: работа с карточками, этапами, файлами, заявками и импортом. Просмотр журнала через API доступен администратору. Криптографическая неизменяемость журнала и регистрация абсолютно всех операций не реализованы.

Наличие этих механизмов **не является подтверждением соответствия всей системы нормативным требованиям или сертификации**. В этом README такое соответствие не заявляется.

## 7. Обновление существующего проекта

1. Сохранить текущие исходники, `.env`, резервные копии PostgreSQL и MinIO.
2. Остановить backend на время копирования всего комплекта, чтобы autoreload не загрузил частично обновлённые файлы.
3. Скопировать `replacement/` из комплекта v3 в корень проекта с сохранением путей.
4. Сохранить прежний `ENCRYPTION_KEY`, проверить параметры Keycloak и MinIO.
5. Запустить backend, проверить журнал и пересобрать frontend.

Пример резервного копирования PostgreSQL:

```sh
docker compose stop backend
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-before-update.sql
```

Проверьте успешное завершение команды. Не используйте `docker compose down -v`: эта команда удаляет постоянные тома.

При старте выполняется аддитивное обновление схемы, включая `workflow_stages.deadline_days` и `partnership_requests`. Требуются права CREATE/ALTER. Первый запуск обновлённого backend выполняйте одним экземпляром. Старые файлы и комментарии без информации об этапе привязываются к текущему этапу взаимодействия; восстановить неизвестную историю автоматически нельзя.
